# 阶段三：核心路径修补与回归测试

## 目标

只修复会阻断保留方法链路的上游缺陷，并为源码裁剪后的核心行为建立自动化保护。

修补不是重新设计方法。

## 1. Emergent subtopic 重复检查

`InterviewTopicManager._check_duplicate_subtopic` 的部分返回路径与调用方解包数量不一致，可能在首次创建 emergent subtopic 时抛出异常。

处理要求：

- 统一所有返回路径的结构；
- 不改变相似度阈值和 duplicate 判定语义；
- 覆盖无 Embedding Service、空 Embedding 索引和正常匹配路径。

## 2. 嵌套 XML tool-call 参数

现有解析器只读取父元素的 `.text`，无法正确恢复 list-of-object 形式的嵌套参数。这会使 emergent insights 和 strategic questions 被静默解析为空。

处理要求：

- 递归解析叶节点、对象和重复子节点列表；
- 在调用工具前执行参数 schema 校验；
- 解析错误必须显式失败，不能当作空结果继续；
- 覆盖 `emergent_insights` 与 `questions` 两条真实方法路径。

## 3. 裁剪回归

使用 fake/mock LLM 响应验证：

- Interviewer、Agenda Manager 与 Exploration Planner 能初始化；
- 删除模拟受访者后，外部回答仍能进入消息流；
- 删除 Evaluation Logger 后，问题去重仍正常工作；
- 删除 baseline 分支后，唯一保留的是 SparkMe 方法路径；
- 无 Web、语音和论文评价依赖时，核心包仍可导入；
- 异常不会留下半提交的消息、Agenda 更新或 strategic state。

## 修补边界

- 不调整 utility 公式；
- 不调整 planner 触发流程；
- 不根据论文重新写 rollout；
- 不增加方法来源、版本或追溯字段；
- 不在 Prompt 中写 issue 编号或修补说明；
- 测试名称描述行为，不描述论文 Figure 或来源。

## 验收标准

- 两个核心缺陷均有最小回归测试；
- 裁剪后的方法主链可以在无真实 LLM、无实验数据条件下完成一次脚本化多轮流程；
- 测试能证明 Agenda、coverage、emergence 与 planner 都实际参与；
- 修补没有引入平行实现或 RE 专用评分逻辑。

## 阶段产物

- 核心缺陷修补；
- 方法级单元与集成测试；
- 不依赖真实模型和论文数据的测试 fixtures。

本阶段的测试、fixtures 和 fake/mock LLM 仅用于开发期验证，不属于最终方法交付资产，在阶段七完成验收后删除。
